# 代码格式与风格规范

本文件规定代码怎么写，是格式与写法约定的唯一来源。技术路线与公共契约见 `docs/ARCHITECTURE.md`，协作流程与验证档位见
`AGENTS.md`。`.editorconfig` 与 `.gitattributes` 是本规范的机器可执行配置，三者的编码、换行和缩进要求必须同步；
发生冲突时以本文件为准，并同步修正配置文件。

## 文件与缩进

- 编码使用 UTF-8；除 Markdown 外去除行尾空格。
- Java、XML、YAML、Markdown、properties、sh 使用 LF；bat、cmd 使用 CRLF。
- Java 文件最后一个非空字符应为最外层类型的 `}`，不保留终止 LF，也不保留末尾空白行；其他文本文件遵循
  `.editorconfig` 的终止换行配置。
- 缩进只使用空格，不使用 Tab：Java、XML 为 4 个空格，YAML、JSON、Markdown 为 2 个空格。
- 行宽上限为 120 列；超出时按语义换行，不为凑行宽拆散完整表达式。
- 不产生与任务无关的格式与换行变化。

## 大括号与换行

- 左大括号与声明同行，右大括号独占一行；分支之间的空行按「空行」执行。这是项目大括号风格，不套用其他风格名称。
- 方法体一律展开为多行，禁止 `public int getCode() { return code; }` 这类单行写法；getter/setter 也让
  `return <field>;` 单独成行。
- 控制流语句一律写大括号，即使只有一条语句。
- 链式调用超出行宽或连续调用超过 2 次时逐行拆分，`.` 置于行首，续行缩进 4 个空格。
- 参数列表超宽时先整体换到一个续行并缩进 4 个空格；单个续行仍超过行宽时按参数语义分组换行，不机械地每个参数占一行。
- 运算符两侧、逗号后、关键字与括号之间保留一个空格。

## 空行

类型声明（类、接口、枚举）内：

- 类体首尾各空 1 行：左大括号与第一个成员之间、最后一个成员与右大括号之间。
- 字段与字段之间空 1 行。
- 字段与方法（含构造器）之间、方法与方法之间（含 getter/setter）空 2 行。
- 枚举常量之间空 1 行；最后一个常量与后续字段之间空 2 行。
- 禁止连续 3 行及以上空行；分节靠注释与成员类型区分，不靠堆空行。

方法体与控制流体内（大括号内侧首尾不空行）：

- `if` / `else if` / `else`、`for` / `while` / `do-while`、`try` / `catch` / `finally` 块与上方语句之间空 1 行；
  同一 `if` 链的相邻分支之间同样空 1 行。
- `switch` 的各 `case` 之间空 1 行。
- 多个独立步骤之间空 1 行分组；简单顺序语句不刻意空行。
- 单条 `return` 不空行；`return` 上方存在分支或循环时空 1 行。

```java
/**
 * 空行与注释写法示例
 */
public class Example {

    /**
     * 应用码
     */
    private final int code;

    /**
     * 响应说明
     */
    private final String msg;


    /**
     * 根据应用码返回可读说明
     *
     * @return 应用码为 200 时返回成功说明，否则返回原始说明
     */
    public String describe() {
        // 成功应用码使用统一说明，其他应用码保留原始说明
        if (code == 200) {
            return "成功";
        }

        return msg;
    }

}
```

## import

- `package` 与 import 块之间空 1 行；import 块与类级 Javadoc（或首个注解）之间空 1 行。
- 普通 import 排为两组：非 `java.*` / `javax.*` 的 import 按包路径字母顺序排成一个整体块，中间不插空行；
  `java.*` 与 `javax.*` 集中放在该块之后，与前者空 1 行。该布局与 IDEA 默认的 import 布局一致，可直接使用
  IDEA 的格式化结果。
- 静态 import 集中放在普通 import 之后，与前者空 1 行。
- 不保留未使用的 import；不用通配符 `*` 代替具体类型；不用全限定类名代替 import，除非类名冲突。

## 命名

- 类、接口、枚举使用 `UpperCamelCase`；方法、字段、局部变量和参数使用 `lowerCamelCase`；常量使用
  `UPPER_SNAKE_CASE`。
- 包名全小写，与目录一致，不使用下划线和连字符。
- 名称使用完整业务术语，不用无意义缩写；同一概念只用同一个词，跨文件的术语一致性见「文档一致性」。

## 注解

- 类、字段、方法的注解各占一行，紧贴声明行。
- Javadoc、注解、声明行之间不空行，视为一个整体块。
- 参数级注解（`@RequestBody`、`@Valid`、`@PathVariable` 等）与参数同行。
- 覆写方法必须写 `@Override`；标注 `@Deprecated` 时在 Javadoc 用 `@deprecated` 说明替代方案。
- 多个注解的顺序不强求统一，按 Spring、Jakarta、Lombok 的常见排列即可。

## Javadoc 与注释

- 源码中声明的类、接口、枚举、注解类型（`@interface`）、枚举常量、字段、构造器和方法都写 Javadoc，
  不因可见性低、逻辑简单或位于测试代码而省略。
- 测试方法的 Javadoc 写明用例目的、主要前提和断言重点；测试夹具字段与测试构造器同样写明用途。
- 内容说明职责、业务约束、输入输出或设计原因，不逐字翻译代码，不记录作者、创建时间和修改历史。
- Javadoc 与 `//` 注释的末尾不加句号；一段注释包含多句时，句与句之间仍用句号分隔，仅省略最后一句的句号。
- 字段 Javadoc 用中文描述字段含义，直接以中文术语开头，不重复英文字段名；引用其他成员使用 `{@link ...}`。
- 含义相同的字段在不同类中的注释保持一致的语义表述与取值说明，差异部分单独注明。
- 类级与成员级使用 `/** ... */`，语句级说明使用 `//`。
- 方法体内的 `if`、`for`、`switch`、`while`、`do-while`、`try` 等控制流块都在上方用 `//` 说明目的或原因；
  意图一致时，一条注释可以覆盖完整的 `if/else if/else` 或 `try/catch/finally` 链，分支意图不同时分别说明。
- 局部变量和参数不单独写 Javadoc；需要补充语义时，在所属方法中使用 `@param`、`@return`、`@throws` 说明。
- 同一 Javadoc 块内有多个 `@param` 时，按最长参数名在较短名称后补空格，使各行说明列起始位置对齐。

## XML 与配置注释

- `pom.xml` 为 Parent、properties、依赖、插件、execution、编译阶段和注解处理器等配置块保留简洁注释，说明用途、
  生效范围或采用原因；对不熟悉的配置机制（如生命周期阶段、默认任务标识）可以加解释性注释帮助理解，
  但对含义显然的坐标标签（`groupId`、`artifactId` 等）不逐行翻译。
- YAML 和 properties 为非显然的取值、单位、环境差异、安全影响或配置原因添加注释。
- 修改配置时同步核对 README、架构与公共契约文档和相关测试，避免注释与实际行为脱节。

## Spring 与系统边界

- Jakarta EE API 使用 `jakarta.*`，不使用旧的 `javax.*` 包名。
- Spring 组件使用构造器注入，不使用字段注入，也不通过静态变量获取 Spring 容器。
- 成组配置使用类型安全的 `@ConfigurationProperties`；密钥通过环境变量或密钥服务注入，不写入仓库。
- 在系统边界校验输入，在领域内部保证业务不变量；Controller 和外部适配器的职责边界遵守 `docs/ARCHITECTURE.md`。
- 版本化 Controller 用 `ApiVersions.VERSION_PATH_TEMPLATE` 声明路径时，类上添加
  `@SuppressWarnings("MVCPathVariableInspection")`，并在类 Javadoc 说明路径变量仅承担版本段路由约束、
  版本值由 API Versioning 解析；未版本化 Controller 不涉及该模板，不添加此抑制。
- 日志使用参数化写法，生产代码禁止 `System.out.println` 与 `printStackTrace`。不记录密码、验证码、令牌、密钥、
  原始会话凭证和完整请求体；个人信息默认不记录，确有业务或审计需要时最小化并脱敏。可以记录不含敏感信息的请求 ID
  与追踪 ID。

## 类型与不可变

- 永远有值的字段使用基本类型（`int`、`long`、`boolean` 等），避免 null 语义歧义；仅在需要表达「未设置 / 已设置」
  二态时使用包装类型，并显式处理 null。
- 字段由基本类型改为包装类型会改变公共 API 行为，按 `AGENTS.md`「必须先确认的变更」处理。
- `common/` 下的载体字段全部使用 `final`，通过私有构造器与静态工厂方法创建。
- 金额使用 `BigDecimal` 并明确币种与舍入规则；时间使用 `java.time` 并明确时区语义。

## 编码习惯

- 一个方法只做一件事；确需分步时按步骤用空行分组。
- 参数校验与失败场景前置 `return` 或抛出异常，主路径不深层嵌套 `if`。
- 局部变量在使用处附近声明，不在方法开头堆放；局部变量与参数不强制添加 `final`。
- 类型内的成员按枚举常量、静态常量、实例字段、构造器、方法的顺序排列。
- 优先使用小而明确的类型和组合，不提前抽象；不应预设的通用层见 `docs/ARCHITECTURE.md`「模块化单体架构」。
- 单个源文件只放一个顶级类型；辅助类型优先使用静态嵌套类。
- 不吞异常，不用未说明的 `null` 表示失败。

## 测试写法

本节只规定测试怎么写。是否需要测试、测试层级与验证档位见 `AGENTS.md`「测试与验证」。

- 测试类使用被测类型名加 `Tests` 后缀，与被测代码同包；场景复杂时使用嵌套测试类分组。
- 测试方法使用 `<被测行为>Should<期望结果>` 命名，不加 `test` 前缀。
- 普通单元测试使用 AssertJ 的 `assertThat(...)`；MockMvc 切片测试使用 `andExpect(...)` 匹配器。
- 同一方法的不同输入使用独立用例；只有取值不同且断言完全相同时才使用参数化测试。
- 不为已被其他测试覆盖且没有新增价值的行为重复编写用例。

## Markdown

- 一级标题只用于文件标题，正文从 `##` 开始，不跳级。
- 无序列表使用 `-`，有序列表使用 `1.`。
- 代码块必须声明语言（`java`、`text`、`powershell`、`xml` 等）。
- 表格使用标准 Markdown 语法，不强求源文件列宽对齐。

## 文档一致性

- `README.md` 项目结构树中的注释必须与对应文件的实际标题或既定职责一致；新增、重命名或拆分文件时同步更新，
  不沿用过期别名。
- 结构树按目录层级缩进，`├──` / `└──` 视位置决定，右侧注释使用 ` # ...`。
- 同一模块的业务术语与职责描述在 README、配置、注释、测试和接口文档中保持一致；职责变化时同步更新全部相关位置。
