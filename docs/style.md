# 代码格式与风格规范

本文件规定代码怎么写，是格式与写法约定的唯一来源。技术选型见 `docs/decisions.md`，协作流程与验证档位见 `AGENTS.md`。基础格式由 `.editorconfig` 与 `.gitattributes` 锁定，本文件不重复其中已有的配置项。

## 文件与缩进

- 编码 UTF-8；文件末尾保留单个换行；除 Markdown 外去除行尾空格。
- 换行符：Java、XML、YAML、Markdown、properties、sh 用 LF；bat、cmd 用 CRLF。
- 缩进只用空格，不使用 Tab：Java、XML 为 4 空格，YAML、JSON、Markdown 为 2 空格。
- 行宽上限 120 列。超出时按语义换行，不为凑行宽拆散完整表达式。
- 不产生与任务无关的格式与换行变化。

## 大括号与换行

- 左大括号与声明同行（K&R 风格），右大括号独占一行。
- 方法体一律展开为多行：禁止 `public int getCode() { return code; }` 这类单行写法，getter/setter 也要让 `return <field>;` 单独成行。
- 控制流语句一律写大括号，即使只有一条语句。
- 链式调用超出行宽或超过 2 环时逐行拆分，`.` 置于行首，续行缩进 8 空格。
- 参数列表超宽时整体换行，续行缩进 8 空格，不逐个参数单独成行。
- 运算符两侧、逗号后、关键字与括号之间保留一个空格。

## 空行

类型声明（类、接口、枚举、`record`）内：

- 类体首尾各空 1 行：左大括号与第一个成员之间、最后一个成员与右大括号之间。
- 字段与字段之间空 1 行。
- 字段与方法（含构造器）之间、方法与方法之间（含 getter/setter）空 2 行。
- 枚举常量之间空 1 行；最后一个常量与后续字段之间空 2 行。
- 禁止连续 3 行及以上空行；分节靠注释与成员类型区分，不靠堆空行。

方法体与控制流体内（大括号内侧首尾不空行）：

- `if` / `else if` / `else`、`for` / `while` / `do-while`、`try` / `catch` / `finally` 块与上方语句之间空 1 行，同一 `if` 链的相邻分支之间同样空 1 行。
- `switch` 的各 `case` 之间空 1 行。
- 多个独立步骤之间空 1 行分组；简单顺序语句不刻意空行。
- 单条 `return` 不空行；`return` 上方存在分支或循环时空 1 行。

```java
public class Example {

    private final int code;

    private final String msg;


    public String describe() {
        if (code == 200) {
            return "成功";
        }

        return msg;
    }

}
```

## import

- `package` 与 import 块之间空 1 行；import 块与类级 Javadoc（或首个注解）之间空 1 行。
- 普通 import 按包路径字母顺序排列，不插入空行分组。
- 静态 import 集中放在普通 import 之后，与前者空 1 行。
- 不保留未使用的 import；不用通配符 `*` 代替具体类型；不用全限定类名代替 import，除非类名冲突。

## 命名

- 类、接口、枚举：`UpperCamelCase`；方法、字段、局部变量、参数：`lowerCamelCase`；常量：`UPPER_SNAKE_CASE`。
- 包名全小写，与目录一致，禁用下划线与连字符。
- 名称使用完整业务术语，不用无意义缩写；同一概念只用同一个词，跨文件的术语一致性见「文档一致性」。

## 注解

- 类、字段、方法的注解各占一行，紧贴声明行。
- Javadoc、注解、声明行之间不空行，视为一个整体块。
- 参数级注解（`@RequestBody`、`@Valid`、`@PathVariable` 等）与参数同行。
- 覆写方法必须写 `@Override`；标注 `@Deprecated` 时在 Javadoc 用 `@deprecated` 说明替代方案。
- 多个注解的顺序不强求统一，按 Spring、Jakarta、Lombok 的常见排列即可。

## Javadoc 与注释

- public 类、构造器、方法、字段必须有 Javadoc；无额外语义的成员（如仅返回字段的 getter、入口 `main` 方法）可不写；私有成员在逻辑不明显时必须写。
- 测试方法必须有 Javadoc，写明用例目的、断言重点或前提条件。
- 内容说明职责、业务约束、输入输出或设计原因；不翻译代码，不记录作者、创建时间与修改历史。
- 字段 Javadoc 用中文描述字段含义，直接以中文术语开头，不重复英文字段名（不写 `code: 业务状态码`）；引用其他成员用 `{@link ...}`。
- 含义相同的字段在不同类中的注释保持一致的语义表述与取值说明，差异部分单独注明。
- 类级与成员级用 `/** ... */`，语句级补充用 `//`。
- 方法体内的 `for` / `if` / `switch` 等控制流块，当意图不能从代码一目了然时，在上方用 `//` 加一句话说明该段逻辑的作用或原因；自解释的简单判断（如空值前置返回）可不加。

## 类型与不可变

- 永远有值的字段用基本类型（`int`、`long`、`boolean` 等），避免 null 语义歧义；仅在需要表达「未设置 / 已设置」二态时用包装类型，并显式处理 null。
- 字段由基本类型改为包装类型会改变公共 API 行为，按 `AGENTS.md`「必须先确认的变更」处理。
- `common/` 下的载体字段全部 `final`，通过私有构造器与静态工厂方法创建。
- 金额用 `BigDecimal` 并明确币种与舍入规则；时间用 `java.time` 并明确时区语义。

## 编码习惯

- 一个方法只做一件事；确需分步时按步骤用空行分组。
- 参数校验与失败场景前置 `return` 或抛异常，主路径不深嵌 `if`。
- 局部变量在使用处附近声明，不在方法开头堆变量；局部变量与参数不强制加 `final`。
- 优先使用小而明确的类型和组合，不提前抽象（不该抽取哪些通用层见 `docs/decisions.md`「采用模块化单体架构」）。
- 单个源文件只放一个顶级类型；辅助类型优先做静态嵌套类。
- 不吞异常，不用未说明的 `null` 表示失败。

## 测试写法

本节只规定测试怎么写。该不该写测试、写在哪一层、验证到哪一档，见 `AGENTS.md`「测试与验证」。

- 测试类命名为被测类名加 `Tests` 后缀，与被测代码同包；场景复杂时用嵌套测试类分组。
- 测试方法命名为 `<被测行为>Should<期望结果>`，不加 `test` 前缀，例如 `successShouldCarryData`。`HelloControllerTests.shouldReturnHelloMessage` 是既有写法，不强制改写。
- 普通单元测试的断言使用 AssertJ 的 `assertThat(...)`，以静态 import 引入；MockMvc 切片测试使用其自带的 `andExpect(...)` 匹配器。
- 用例粒度：同一方法的不同入参拆成独立测试；若两个用例只有取值不同且断言相同，合并为一个测试。
- 不为已被其他测试覆盖的行为重复写用例。

## Markdown

- 一级标题只用于文件标题，正文层级从 `##` 开始，不跳级。
- 无序列表用 `-`，有序列表用 `1.`。
- 代码块必须声明语言（`java`、`text`、`powershell`、`xml` 等）。
- 表格使用标准 Markdown 语法，不强求源文件列宽对齐。

## 文档一致性

- `README.md` 项目结构树中的注释必须与对应文件的实际标题或既定职责一致；新增、重命名、拆分文档时同步更新，不沿用过期别名。
- 结构树按目录层级缩进，`├──` / `└──` 视位置决定，右侧注释用 ` # ...` 形式。
- 同一模块的业务术语与职责描述在 README、配置、注释、测试、接口文档中保持一致；职责变化时同步更新全部相关位置。
